# 3D 火车沙盘游戏 · 概要设计（v1.1）

> 目标读者：项目所有者（review 用）
> 状态：**v1.1** — D1–D8 已确认（见 §10）；**M1 / M2 的 `core/` 部分已实现并测通**（269 条回归测试），渲染层尚未开始。各章标注的"实测结论"都是已经跑出来的数字，不是估算。

## 1. 目标与范围

### 1.1 一句话定义
一个用 Python 编写的 **3D 铁路沙盘**：在一块场地上用"轨道件"拼出**闭环**线路（圆环、交叉、8 字形、双环等），放入多种中国铁路列车（绿皮车、和谐号、复兴号）在线上自动或手动运行，并用车站、建筑、绿化、山体、桥梁等布景把场地布置成一个微缩世界。

### 1.2 必须做到（v1 验收线）
| 编号 | 能力 | 验收方式 |
|---|---|---|
| G1 | 放置铁轨并**组成闭环** | 拼出圆环 / 8 字形 / 带交叉的双环，闭环误差 < 1 mm（**已用公式实测算得 1.5e-14 m**，见 §5.5） |
| G2 | 列车沿闭环**连续运行不脱节** | 8 节编组绕环 10 圈，车厢间距误差 < 5 cm，转向架始终在轨 |
| G3 | **至少 3 种列车**可选并外观可辨 | 绿皮车 / 和谐号 / 复兴号，涂装与编组可区分 |
| G4 | **布景**：车站、建筑、绿化、山体、桥梁 | 5 类均可放置、可删除、可存档 |
| G5 | **存档 / 读档** | 布局 + 地形 + 布景 + 列车完整还原，往返无差异 |

### 1.3 明确不做（v1 非目标）
- 多人联机、云存档
- 真实脱轨 / 碰撞刚体物理（列车是"沿轨运动学"，不是物理仿真）
- 自由曲面轨道（道岔角度、半径不可自定义，只用目录里的标准件）
- 移动端 / VR / 网页版
- 真实铁路信号闭塞系统（只做简单的道岔与限速）
- 大地形流式加载（v1 固定尺寸场地）

## 3. 技术选型

### 3.1 渲染 / 引擎

| 候选 | 版本 | 结论 | 理由 |
|---|---|---|---|
| **Panda3D（直用 API）** | 1.10.16 | **推荐** | ① 有 cp314 轮子，本机可装；② 自带场景图、GLSL、碰撞射线拾取、实例化、`Geom` 底层网格构建、glTF 加载（`panda3d-gltf 1.3.0`）；③ 做一个"编辑器类"应用需要精确控制场景图与自定义网格，Panda3D 给得足够底层；④ 纯 Python 绑定，调试成本低 |
| Ursina | 8.3.0 | 备选 | 上手最快，但它是对 Panda3D 的一层"游戏循环 + 实体"封装，强项在快速做小游戏；本项目主要复杂度在**自定义几何 + 编辑器交互状态机**，Ursina 的封装反而挡路，且会绑定它的 panda3d 版本 |
| pyglet + PyOpenGL | 2.1.16 / 3.1.10 | 不推荐 | 一切都要自己写（场景图、拾取、字体、网格工具），工期 ×3 |
| Godot / Unity | — | 排除 | 不是 Python |

> 说明：**不选 Ursina，但会借鉴它的调用手感**（例如 `entity.position += ...` 这类糖）。迁移成本被压在 `render/` 一层内，若将来想换，只改这一层。

### 3.3 环境（建议新建专用环境，不要污染 base）

```powershell
conda create -n train3d python=3.12 -y
conda activate train3d
pip install panda3d==1.10.16 numpy
```

选 **3.12** 而不是 base 的 3.14：3.12 是当前所有可选库（glTF、simplepbr、PySide6 等）轮子最齐的版本。若你希望直接用 base 的 3.14，核心功能同样可行（panda3d 有 cp314 轮子），代价是个别可选库可能装不上。

### 3.4 UI 方案
**Panda3D DirectGUI**（自带，零依赖）+ 自绘 HUD。理由：核显机器上再叠一层 UI 框架（PySide6 / WebView）会带来跨进程或跨窗口的复杂度；DirectGUI 虽朴素但可控，且我们会把它包在 `ui/` 一层后面，将来换 `imgui`（PyPI `imgui 2.0.0`）只改这一层。

> ⚠️ **中文字体是个真坑**：Panda3D 默认字体不含 CJK 字形，不处理会满屏方块。必须 `loader.loadFont()` 加载系统字体（如 `C:\Windows\Fonts\msyh.ttc` 微软雅黑，或随包附带思源黑体），并在启动时统一注册为默认字体。已列入 M0 任务。

## 4. 总体架构

### 4.1 分层（核心原则：几何与仿真逻辑不依赖引擎）

```
┌─────────────────────────────────────────────────────────┐
│ app/          应用层：状态机、工具、输入、主循环、UI 装配   │  ← 唯一知道"引擎"的地方之一
├─────────────────────────────────────────────────────────┤
│ render/       渲染层：场景构建、网格生成、材质、光照、相机  │  ← 唯一直接调用 panda3d 的地方
├─────────────────────────────────────────────────────────┤
│ core/         核心层：纯 Python + numpy，无引擎依赖        │  ← 可 headless 单元测试 ★
│              轨道几何 / 装配图 / 路径求解 / 列车运动学 / 地形 │
├─────────────────────────────────────────────────────────┤
│ data/         数据层：品类目录（轨道件、列车、布景）JSON    │
└─────────────────────────────────────────────────────────┘
```

**为什么要把 `core/` 做成纯 Python**：轨道闭环精度、8 字构造、列车跟随运动学这些东西最容易出隐蔽 bug，而它们**完全不需要显卡**。把 `core/` 独立出来后，可以用 pytest 在几毫秒内回归验证"8 字是否精确闭合"，不用开窗口、不用渲染。这是整个架构里最重要的一条决定。

```
依赖方向：app → render → core ← data
              app ──────────┘
core 永远不 import panda3d
```

## 5. 核心设计（本项目真正的难点都在这一节）

### 5.1 轨道几何：一个公式统一"直轨"和"弯轨"

**约定**：世界坐标右手系，`+Y` 为上，地面为 `XZ` 平面。轨道件在**自身局部坐标系**里定义，方位 = 位置 `(x, y, z)` + 航向角 `θ`（从 `+X` 轴向 `+Z` 轴旋转）+ 俯仰角 `φ`。中心线的切向量 = `(cosθ, 0, sinθ)`。

把轨道件的中心线只看成「**一段等曲率的圆弧**」，参数是弧长 `L` 与总转角 `Δθ`：

- 直线：`Δθ = 0`
- 弯轨：`Δθ = ±45°`，曲率半径 `R = L / |Δθ|`

从起点（局部原点，航向 0）走到终点，终点位姿有**闭式解**（复平面上积分 `dp/ds = e^{iθ(s)}`）：

```
p(L) = L · (e^{iΔθ} − 1) / (iΔθ)          （Δθ → 0 时退化为 p = L，即直线）
θ(L) = Δθ
```

**这个统一的直接好处**：

1. 一种数据结构覆盖所有"沿轨"件，不需要为直线写特例分支；
2. 因为是解析式，**拼接是精确的**——不是"足够接近然后吸附"，而是数学上严丝合缝（误差仅来自 float 舍入）；
3. 闭环能否成立的判据变得非常干净：**只要航向角总和是 360° 的整数倍，且半径一致，就必然闭合**。例如 8 段 45° 等半径弯轨 = 一个精确的圆环。

### 5.2 端口（Port）驱动的拼装：为什么不用"网格吸附"

两种做法：

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 网格吸附 | 位置吸附到格点，角度吸附到 45° | 45° 圆弧的弦长是无理数（`2R·sin22.5°`），**永远吸不上格点**，会留下一堆微小缝隙，"看起来接上了但差 3 cm"，列车经过时会跳 |
| B. **端口吸附** | 每个轨道件有若干**端口**，端口带位姿；新件的某个端口吸附到已有件的空闲端口上，位姿由**父件位姿 × 局部位姿**算出 | 无缝隙，闭环精确；代价是位置不再是"整数格点"，但这只影响内部表示，用户看不见 |

**选定 B（端口驱动）**。要点：

- 轨道件的位姿**不是用户输入的自由量**，而是由吸附链**推导**出来的。用户拖动的只是"我要把这个件挂到那个口上"。
- 布景（树、房子）仍然用"位置 + 角度"自由放置 + 网格吸附，因为它们没有必须精确对接的语义。
- 端口可以**不连接**（例如 8 字形的相切点，或两条线只是视觉上交叉），因此需要区分 `port.connected_to = None | PortRef`，并且提供"**视觉交叉但不连通**"的显式标记。

### 5.3 件目录：端口 + 路由

每个轨道件定义成（`data/pieces.json`）。关键改动：**目录里只写一份几何，端口位姿由 `route` 推导**，不手写端口坐标：

```jsonc
{
  "id": "curve_r40_l45",
  "name": "左弯轨 R40 / 45°",
  "category": "curve",
  "mesh": "ballast",              // 道床 / 桥面 / 高架 用同一几何、不同外观
  "routes": [
    // 每一条 route =「从 from 端口走到 to 端口」的一段等曲率圆弧
    { "from": "a", "to": "b", "radius": 40.0, "dtheta_deg": 45.0 }
    // 也可直接给 "length"；弯轨给 "radius" 更自然
    // 可选 "offset_deg"（把整条 route 绕件原点转）与 "translate"（先平移）
    // 可选 "grade"：每单位平面弧长的高程变化（0.03 = 3% 上坡）
  ]
}
```

**端口位姿的推导规则**（`core/track/catalog.py`）：

1. 在 route 自己的局部坐标里，入口「行进帧」是原点、heading = 0；出口行进帧是 §5.1 公式算出的 `arc_end_pose(length, dtheta)`。
2. route 可选用 `translate` / `offset_deg` 摆到件坐标系，次序是「**先平移、后旋转**」——这样 `offset_deg = 45` 的等长 route 是绕件原点旋转，而不是绕自己转（交叉件靠这一点对齐）。
3. 端口的**外指向**由行进帧推出：入口端口的外指向 = 行进方向掉头 180°，出口端口的外指向 = 行进方向。

这条规则的收益是**目录数据不可能自相矛盾**：端口不是"另一份手写数据"，而是几何的推论。而且反过来还能**反解**——任意两个端口，当且仅当它们的位姿落在同一条等曲率圆弧上时才定义出一条合法路由（判据是 §5.1 推导出的切线条件 `dz/dx == tan(dtheta/2)`）。因此 `Catalog.validate()` 可以把每条 route 反解回去和声明值对一遍，**写错立刻报错而不是留下一道 3 cm 的缝**。

`routes` 是**整个路由模型的核心**：

| 件 | `routes` | 语义 |
|---|---|---|
| 直轨 | `[["a","b"]]` | 一条通路 |
| 弯轨 | `[["a","b"]]` | 一条通路 |
| 菱形交叉 45° | `[["a","c"], ["b","d"]]` | 两条**互相独立**的通路，列车直穿、**不能转弯** |
| 道岔（右开） | `[["a","b"], ["a","c"]]` | 两条通路**共享入口** → 必须靠道岔状态选路 |
| 缓冲端 | `[]` | 死端，列车到此停车/折返 |

于是"列车能不能走通"就不需要任何特殊逻辑了：从某个入口端口出发，沿当前件 `routes` 里入口匹配的那条走到出口，再走到相连端口的下一件，如此递归。**闭环 = 这个游走回到了出发点**。

方向也是统一的：反走同一段弧就是**同一段几何反向通过**（弧长不变、总转角取负），因此走线代码里没有"正向/反向"两套分支。道岔的三档差异全部体现在 `routes` 数据里；**"死端"就是 `routes` 为空**（缓冲端），因此三者共用同一段走线代码，没有任何 `if piece.type == ...`。

### 5.4 闭环检测
游走过程中累计位移。若回到起始端口时位置误差 < **1e-6 m** 且航向误差 < **1e-9°**，判定闭环成立；否则 UI 在"缺口"处画红色标记并提示差多少。

阈值之所以能卡得这么死，是因为 §5.1 是解析式：**真正闭合的环误差在 1e-14 m 量级（就是 float64 的舍入极限）**，而不闭合的环（少一节、半径不一致）误差是米级的。两者相差 14 个数量级，**不存在中间地带，因此不会误判**——这比"宽容差 + 视觉吸附"可靠得多。

### 5.5 8 字形为什么能拼出来（这点先确认清楚，避免后期返工）

直觉上"8 字"需要一个 45° 交叉，其实**不需要**：

- 取半径 R 的 45° 弯轨，**同向连 8 节** → 精确画出一个整圆（转角 8×45° = 360°）；
- 再**反向连 8 节** → 画出第二个整圆；
- 两个圆的圆心分别在起点航向的**左右两侧、距起点各 R**，所以圆心间距恰好 `2R` → **两圆精确外切**，切点就在接缝处。

结果就是标准 ∞ 形（8 字），列车在切点处从第一个圆平滑进入第二个圆，路径上没有任何 X 形交叉件。**结论：只用「直线 + ±45° 弯轨」就能拼出圆环与 8 字**；菱形交叉件是为了别的玩法（立体交叉、双环、站前交叉渡线）才需要的。

**这条已经用公式实测验证过了**（`R = 40 m`，float64）：

| 构造 | 航向总转角 | 终点偏差 | 结论 |
|---|---|---|---|
| 8 × 45° 同向 | 360.000000° | **1.5e-14 m** | 精确闭合为圆 |
| 16 × 22.5° 同向 | 360.000000° | **2.8e-14 m** | 精确闭合为圆 |
| 4 × 90° 同向 | 360.000000° | **1.6e-14 m** | 精确闭合为圆 |
| 8 × 45° 后接 8 × (−45°) | 360° → 360° | 两环均 **1.5e-14 m** | 8 字形精确闭合 |
| 两环圆心距 | — | **80.000000 m = 2R** | 精确外切，接缝无折角 |

（22.5°、45°、90° 三种转角规格都验证可用，因此道岔分叉角选 22.5° 也有现成几何支撑。）

这一条会写成回归测试：`test_figure_eight_closes_exactly()`。

### 5.6 列车跟随运动学：转向架模型（让"像火车"的关键）

不要把车厢当成"沿着路径串起来的盒子"。正确做法是**每节车有两个转向架**：

```
车 i 的两个转向架中心在弧长 s_i ± b 处（b = 转向架半距）
车体中心 = 两转向架中点
车体航向 = 转向架2位置 − 转向架1位置 的方向
车体俯仰 = 两转向架处轨道高度差
车轮 = 挂在转向架位置上（在弯道上自动"内切"，视觉正确）
```

前后车用"相邻两车的**车钩面**之间留出车钩间隙"递推（比直接递推转向架间距更贴近真实连挂关系）：

```
center_0     = s_0 − b_0
center_{i+1} = center_i − 车长_i/2 − 车钩间隙 − 车长_{i+1}/2
```

这样做的好处：过弯时车体会自然地"切内弦"（真实列车就是这样），过关节点不会有车厢穿模；而且**完全不需要物理引擎**，纯运动学、绝对稳定、帧率无关。

> **实测结论（M2 已验证）**：转向架到圆心的距离误差在 `1e-14 m`（float64 噪声），编组跨过接缝（弧长取模变负）也不会跳。车体航向恰好等于「弧长中点处的切线方向」，因此它相对前转向架切线**恰好滞后 `b/R`**——`R = 40 m`、`b = 3.5 m` 时约 5°。这就是"切内弦"的精确量值。

### 5.7 纵向动力学（1D，足够真实且几乎不耗性能）

只沿轨道方向做一维动力学：

```
m · dv/dt = F_牵引(v, 手柄位) − F_制动 − (A + B·v + C·v²) − m·g·sin(坡度)
约束：F_牵引 ≤ μ · m_黏着 · g      （黏着极限）
```

各车差异全部落在参数上，这就是"绿皮车和复兴号的差别"在代码里的体现：

| 车型 | 编组 | 最高速 | 牵引特征 | 备注 |
|---|---|---|---|---|
| 老式绿皮车（22/25B 型） | 机车 + 10~16 辆 | 100 km/h | 动力**集中**（1 台机车拉） | 起步还行、**维持不住**，爬坡吃力 |
| 和谐号 CRH380A | 8 辆动车组 | 350 km/h | 动力**分散** | 起步快 |
| 复兴号 CR400AF/BF | 8 / 16 辆动组 | 350 km/h | 动力分散、黏着质量占比更高 | 加速性最好 |

> 这套参数化设计让"换车"变成换一行 JSON，而不是写代码。

**黏着质量是自动产生差异的关键。** 可达牵引力上限 = `μ × 黏着质量 × g`，而黏着质量 = **所有动力车的质量之和**。于是：

- 绿皮车是「动力集中」，只有 1 台机车 138 t 提供黏着 → 上限 338 kN；
- 动车组几乎全列动力，367 t 都是黏着质量 → 上限 900 kN。

**两种牵引方式的区别不需要写任何 `if`，它是数据的推论。**

> **一处需要修正的预判（M2 实测）**：原先笼统写的"绿皮车起步慢"其实**不准确**。机车的起步牵引力是按车钩强度设计的（300 kN 对 138 t 机车而言很大），因此 80 km/h 以下绿皮车的起步加速度（≈0.42 m/s²）并不比动车组（≈0.70 m/s²）差太多。
>
> **真正的差距有两处**：① 拐点速度——绿皮车 **24 km/h** 就转入恒功率段（之后越来越没劲），复兴号要到 **152 km/h**；② 功率质量比——`2.9 W/kg` 对 `30 W/kg`，**相差 10 倍**。结果：0→100 km/h 绿皮车要 **172 s**，0→200 km/h 复兴号只要 **85 s**；且绿皮车在 1% 坡上就只能跑到 82 km/h，5% 坡上**根本起不来**（阻力 337 kN > 牵引能力 300 kN）。这些数字都在 `scripts/calibrate_trains.py` 里可复现。

### 5.8 尺度：一个旋钮统一"轨道 / 列车 / 建筑"

真实干线列车的最小曲线半径是几百米，而沙盘要的是"看得见的弯"。按真实尺寸做，结果一定是车比弯道还长，非常难看。因此：

- **世界单位 = 米**（沙盘场地尺寸用它描述），轨道件几何按"沙盘尺度"取：直轨 `L = 20 m`、弯轨 `R = 40 m`、45° 转角、轨距 1.435 m。
- 列车、建筑按**统一缩尺系数** `SCALE_MODEL ≈ 0.4` 生成：一节真实 24.5 m 的客车 → 世界长度约 9.8 m。
- 半径 / 车长 ≈ 4 : 1，这正是 N 比例模型铁路的手感——过弯好看，且整列车绕圆环约 1/3 圈。

`SCALE_MODEL` 是**全局唯一**的缩放旋钮，所有车辆与建筑生成器都读它。避免"各做各的缩放"最后套不上。

> **只缩几何，不缩质量与功率（M2 定下的决策 D7）。**
>
> 动力学是沿轨道的一维问题，只与 `v / 牵引 / 阻力 / 质量 / 坡度` 有关，与视觉尺度无关。因此：**长度按 0.4 缩，质量与功率保持真实值**。
>
> 理由：只有这样，"绿皮车 0→100 km/h 要 172 s、复兴号 0→200 km/h 只要 85 s"这种**加速时间**才有意义。如果把质量也按体积缩到 `0.4³ ≈ 0.064` 倍，加速时间会变成几秒钟，车就全成了玩具，车型差别彻底消失。
>
> 副作用：列车的线性密度是真实的 2.5 倍（长度是 0.4 倍、质量是 1 倍）。这不会造成任何可观察的矛盾——一维动力学不涉及转动惯量、脱轨或牵引力沿车长的分布。
>
> 如果真的想要贴近真实的车辆视觉，**把 `SCALE_MODEL` 调大即可**（例如 0.6）；功率质量比不变，动力学结论不变。

**参数表（v1 实际落库值，见 `data/pieces.json`）**

| 参数 | 值 | 说明 |
|---|---|---|
| 场地 | 400 m × 400 m，高度场 256×256 | 可扩展 |
| 轨距 | 1.435 m | 标准轨 |
| 直轨单元 `L` | 10 / 20 / 40 m | 三种变体都已入库 |
| 弯轨半径 `R` | 40 m（45° 的弧长为 31.416 m） | 另备 R80；转角 22.5° / 45° / 90° |
| 道岔分叉角 | 22.5° | 左右开各一 |
| 交叉 | 菱形 45° / 90° | 4 端口、2 条互不相通的通路 |
| 缓冲端 | 零长度车挡，`routes: []` | 只贡献一个端口 |
| 坡道 | 40 m / 3% | 上下坡各一 |
| 轨枕间距 | 1.0 m | 程序化生成 |
| 8 节编组 | ≈ 84 m | 圆周长 251.3 m，占 1/3 |

> **关于横断面：它不跟着 `SCALE_MODEL` 缩。**
> 轨距 1.435 m 是**不缩尺**的（它和轨道件共用同一个值）。若车体横断面也缩到 0.4 倍，全宽只有 1.24 m —— 比轨道还窄，车会"悬在钢轨里面"。所以断面取真实值约 0.9 倍：**全宽 2.8 m、车高 3.6 m**（真实 3.1 m / 4.05 m）。代价是车看起来比真实短粗，这个代价由"`R = 40 m` 的弯道"这一设定决定，本节的 4 : 1 手感已经接受它。

### 5.9 车体外观：把"长什么样"变成可校验的数据（M4 第一步）

参数化车体的三条输入（§9 风险表里列出的那三条）现在全都落在 `data/trains.json` 的 `shape` 里，schema 升到 2：

| 输入 | 数据 | 为什么这么切 |
|---|---|---|
| 车身横截面轮廓 | `profile`：**半断面**折线，从底面中线 `(0, 地板高)` 到顶面中线 `(0, 车顶高)` | 车体左右对称，写一半再镜像，就不可能出现"左边比右边宽 3 mm"。约束只有两条：中段横向坐标为正、高度单调不降 —— 它们一起保证镜像后轮廓**不自交**（每条水平线最多交两次，这正是一个简单多边形的判据） |
| 头部收敛曲线 | `nose`：`scale(u) = end_scale + (1 - end_scale) · (u / length)^power`，`u` 是距车端面的距离 | `power` 小 = 端部钝圆（客车端部倒角），`power` 大 = 端部尖长（CRH380A）。`pivot_height` 是缩放支点，断面**关于这条水平线**收缩，于是鼻尖自然落在腰线附近而不是被拉到车顶或车底 —— 这就是动车组"低伏前伸"的来源 |
| 门窗与色带 | `windows` / `doors` / `stripe`：只给"几扇、多宽、中心距多大"与高度区间 | 沿车长的位置由 `CarSpec.window_bands()` 在"鼻锥与车门之间剩下的连续空档"里**居中算出来**。于是"窗切进了门里""窗户放不下"在构建期就抛错 |

**没有"半宽 / 车高 / 地板高"这类标量。** 它们全是断面的推论（`CarShape.half_width` 等）。同一个尺寸写两遍，就一定会有一天对不上。

**"外观可辨"（G3）因此变成了一条数值断言**：三款车头收敛段占车长的比例必须拉开，且顺序与真实车型一致 ——

| 车型 | 头车收敛段 / 车长 | `power` | 侧影 |
|---|---|---|---|
| 东风4B 内燃机车 | 3.2 % | 1.00 | 棱角分明的方头 |
| 复兴号 CR400AF | 15.5 % | 1.05 | 较短的"剑形"车头 |
| 和谐号 CRH380A | 23.0 % | 1.70 | 细长尖鼻 |

不用等出图：`tests/test_consist.py` 直接量这些比例、量鼻尖断面高度是否小于整车高度的 35 %、量断面镜像后是否自交。

### 5.10 视角拖拽：方向只能靠"体感"验收

环绕相机只有五个自由度（目标点、距离、方位角、俯仰角），代码上怎么写的都对，唯独
**拖拽方向**是个没有正确答案在代码里的东西：往右拖，是"相机往右绕"还是"画面往右走"？
两个都自洽，用户只会说"反了"。

定下来的是**"抓住画面拖"**（和 Google Earth / 地图类应用一致）：

| 操作 | 画面 | 相机的实际位移 |
|---|---|---|
| 鼠标往右拖 | 场地的东西往右走 | 相机朝**屏幕左**绕 |
| 鼠标往上拖 | 场地的东西往上去 | 相机**压低**（俯仰角变小） |

环绕与平移**共用同一条约定**（`pan` 里整体乘 −1），否则会出现"横向跟手、纵向反着"
这种最难受的组合 —— 早期版本正是如此。

**怎么测**：断言不能写在 `azimuth` / `elevation` 的正负号上（那只是把实现抄一遍），
而是量**相机自身往哪动了**：把相机的世界位移投影到它自己的"屏幕右 / 屏幕上"两个
方向，拖右时必须为负（相机退，画面才进）。`tests/test_camera.py` 就是这么量的，并且
`tests/test_app_editor.py` 从"人拖鼠标"那一头再量一遍 —— 中间还夹着 Panda3D 归一化
鼠标坐标（y 向上为正）与窗口尺寸缩放，任何一环符号弄错，表现都一模一样。

### 5.11 音效：为什么"没有声音资源"反而是个约束

音效与布景、轨道件同一个理由：**仓库里没有任何要下载或提交的二进制资源**（§4.2）。
行驶声与风笛都是几段确定性波形，用 `numpy` 现算 → 写成临时 WAV → 交给 Panda3D 的
音频管理器循环播放。同一个种子每次合成逐样本一致，因此"改坏了"能被测试抓住。

关键约束全在**循环无缝**上：片段长度是 1 s / 1.8 s，所以每个频率分量都必须取
**整数 Hz** —— 这样首尾样本天然相接，不需要交叉淡化，接缝处一个样本都不差。宽频轰鸣
因此也不能用"白噪声 + 低通滤波"（循环接头必然有个台阶，听起来是"咔"），而是用
**几十条整数 Hz、随机相位的正弦按 `1/f^decay` 加权叠加**：听感上与噪声无异，却严格周期。

**"不要嘀嘀声"**（用户直接点名的听感要求）在实现上落成两条：行驶声里

1. **不做快速振幅调制** —— 每秒几下的调制听起来就是打点 / 蜂鸣。旧版在 46 Hz 谐波堆
   上叠了 6 Hz、深度 28% 的颤音，那正是"嘀嘀"的来源；
2. **不放孤立的纯高频正弦** —— 旧版的 380 / 570 Hz 两条纯音在变速播放时最像电子提示音。

于是音色改成三层：整数倍频的**牵引谐波堆**（有音调感，改播放速率就像提速换挡）+
低频**宽频轰鸣**（厚度）+ 极少量高频气流（速度感）。轮轨"哐当"声则整条删掉 ——
它一提速就变成密集的嗒嗒嗒，是"嘀嘀"的另一个来源，而用户要的是"只要引擎声"。

这两条听感被写成了断言（`tests/test_audio.py`）：把包络**带通到每秒 3~15 下**再量
调制深度，本波形必须远低于一个用旧版颤音合成的**对照样本**。带通是必须的 —— 宽频轰鸣
本身的包络就是随机起伏的，直接量 `std/mean` 会得到二十几个百分点的"噪声长相"，但那
不是打点。频谱那一条同理：高频段占比必须极小。

> 合成结果按**修订号**落在临时目录（`%TEMP%/train3d_sfx_r<修订号>`），文件名幂等复用。
> 改了波形却不 +1，用户机器上会继续用旧 WAV，表现是"改了没生效"、看起来完全不像缓存
> 问题（见 §11 的真 bug 清单）。

## 6. 关键流程

### 6.1 放置一节轨道
```
鼠标移动到场景 → 射线拾取地面/已有件端口 → 高亮最近的可用端口(容差 5 m)
→ 选择件类型 → 预览件(半透明) → 左键确认
→ core/layout.attach(piece_def, target_port, my_port)
→ 计算位姿 → 检查碰撞/闭环 → 更新装配图 → render 增量重建网格
```

### 6.2 列车运行
```
装配图 → core/path 找出闭环 → RoutePath(弧长参数化)
→ 每帧: dynamics.step(dt) 得到新的 s_head
→ 由 s_head 递推各车 s_i → 由 s_i 采样 RoutePath.pose_at() 得到各转向架位姿
→ render 更新节点变换（只改变换矩阵，不重建网格）
```

### 6.3 地形与轨道的关系
```
放置轨道时 → 在高度场上沿中心线生成"路基走廊"（自动压平 + 填方/挖方过渡）
若轨道所在处地形低于轨道 > 阈值 → 提示"此处建议放桥"，并提供一件式"自动落桥"（把该段直轨替换为桥梁变体 + 生成桥墩）
若地形高于轨道 → 生成隧道口 + 让山体网格包住该段（山体做实体渲染，列车进入后自然被遮挡）
```

### 6.4 存档
```jsonc
{
  "schema": 1,
  "camera": {...},
  "terrain": { "size": 256, "heightmap_png": "..." },   // 高度场存 16bit PNG，无损且小
  "root":  { "index": 0, "def": "curve_r40_l45", "pose": {...} },
  "pieces": [ { "index": 1, "def": "...", "parent": 0, "parent_port": "b", "my_port": "a" } ],
  "seams":  [ [15, "b", 0, "a"] ],      // 合拢接缝，见下
  "scenery": [ { "kind": "tree_oak", "x":.., "z":.., "yaw":.. } ],
  "trains":  [ { "consist": "cr400af_8", "head_s": 123.4, "v": 0 } ],
  "switches": { "3": 1 }
}
```
轨道件用**父子引用**存储，读档时按拓扑序重建位姿——这样存档文件小、可读、可手工修，而且重建结果与放置顺序无关（确定性）。

**存档里有两类连接，必须分开存（M1 实现时的发现）：**

| 类型 | 存放位置 | 作用 |
|---|---|---|
| **父子链** | `pieces[]` | 构成一棵树，**位姿全部由它推导** |
| **合拢接缝** | `seams[]` | `connect()` 建立的额外连接，把开链合拢成闭环（例如 8 字形在切点处的那道缝） |

一开始只存了父子链，结果发现**闭环会在读档后消失**——因为"最后一节接回第一节"这道缝不是父子关系，而是一个额外的连接（它让图里出现了环）。接缝不影响位姿、只影响拓扑，因此单独一个数组即可。

对应实现：`Layout.to_dict()` / `from_dict()`；回归测试 `test_save_round_trip_preserves_connectivity()`。

| 项 | 预算 |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **编辑器手感做不好**（最大风险） | 即使渲染再漂亮也没人愿意玩 | M1 单独成为里程碑并优先打磨；提供"一键吸附 + 可视化端口 + 撤销栈"；早期就找人试手 |
| 列车/建筑 3D 模型素材从哪来 | 直接影响观感，且涉版权 | v1 采用**参数化程序生成**（见下）；同时提供 `assets/models/` 导入 `.glb` 的口子，你可自行替换 |
| Intel 核显性能 | 掉帧 | §7 的实例化 + 关闭实时阴影策略，从第一天就按预算写 |
| Python 3.14 生态不全 | 个别库装不上 | 专用 3.12 环境 |
| 闭环 / 8 字精度 | 轨道有缝、列车跳 | §5.1 解析式 + `core/` headless 回归测试 |
| 中文字体不显示 | 满屏方块 | M0 就统一注册系统 CJK 字体 |
| DirectGUI 界面朴素 | 观感 | 封在 `ui/` 一层，后续可换 imgui |

**关于"参数化生成列车"具体怎么做**（说明这不是妥协而是可行路线）：中国动车组的车体本质是「**一个横截面沿纵向放样（loft）**」——车身是等截面柱体，车头是横截面尺寸沿一条曲线收敛到零的"鼻锥"。所以只要定义：
1. 车身横截面轮廓（带圆角的多边形，加窗户/车门/裙板的凹陷）；
2. 一条**头部收敛曲线**（CRH380A 是细长尖鼻，CR400BF 是较短的"金凤凰"造型）；
3. 涂装 = 沿车身的**颜色带**（绿皮车的黄带、和谐号的蓝带、复兴号的红/蓝飘带）+ 简化贴图。

这三样都是数据，能做出**一眼能认出是哪款车**的低模（每节 < 3k 三角形）。等你有更好的模型，直接丢进 `assets/models/` 即可，代码不用改。

> 这三条已经落库并且校验好了，具体的数据切法与理由见 **§5.9**（`data/trains.json` schema 2）。`render/train_mesh.py` 是下一步。

## 10. 已确认决策（v1.0 基线）

| # | 决策点 | 选项 | **结论** |
|---|---|---|---|
| D1 | 引擎 | Panda3D 直用 / Ursina / 其他 | ✅ **Panda3D 1.10.16 直用 API** |
| D2 | 列车模型来源 | 程序化生成 / 外部 glTF 导入 / 两者都要 | ✅ **先参数化程序生成，同时保留 `assets/models/` 的 glTF 导入接口** |
| D3 | 玩法定位 | 沙盘观察 / 驾驶操作 / 两者兼备 | ✅ **先做「沙盘观察 + 手柄调速」，驾驶视角后续迭代加入** |
| D4 | 场地与尺度 | 固定 400 m 方块 / 可调大小 | ✅ **固定 400 m × 400 m 起步；场地尺寸与 `SCALE_MODEL` 均做成配置项** |

以下四条是**实现 M1/M2 过程中新定下的**（都是写代码时才暴露出来的选择，详见 §5.3 / §5.7 / §5.8 / §6.4）：

| # | 决策点 | **结论** | 理由 |
|---|---|---|---|
| D5 | 件目录的几何来源 | ✅ **只写 route，端口位姿一律推导**，不手写端口坐标 | 端口成为几何的推论，目录数据不可能自相矛盾；且能反向校验（§5.3） |
| D6 | 缓冲区 / 死端怎么表达 | ✅ **缓冲端 = 零长度车挡，`routes: []`** | "走不通"就是"没有 route"，不需要给缓冲端写任何特例代码 |
| D7 | 缩尺是否作用于质量 | ✅ **只缩几何，质量与功率保持真实值** | 否则加速时间变得毫无参考意义，车型差别消失（§5.8） |
| D8 | 闭环接缝怎么存 | ✅ **存档分 `pieces[]`（父子树）+ `seams[]`（合拢缝）两部分** | 接缝不是父子关系，只存父子链会导致读档后闭环消失（§6.4） |

以上决策确定后，§5 的核心设计（端口吸附 / 解析式几何 / 转向架跟随）与 §7 的性能预算均不再变动，可以直接进入 M0。

### 由这些结论推导出的 v1 边界
- 因为选 D1：`render/` 是唯一接触 panda3d 的一层，`core/` 保持纯 Python —— 后续若想换引擎，只重写 `render/`。
- 因为选 D2：M4 只做**参数化车体 + 涂装**，不做模型资源管线；`assets/models/` 空着也能跑完整游戏。
- 因为选 D3：M2 交付"手柄调速 + 编组运行"，司机室视角（M4）是**加分项而非阻塞项**。
- 因为选 D4：所有几何常量集中在 `data/*.json` 与一处配置里，改数值不用改代码。

**踩到并修掉的真 bug**（这就是为什么坚持 headless 测试 + 真入口冒烟）：

1. **`build_piece` 把 `Pose` 当 `Port` 存了** —— 类型标注骗过了肉眼，测试立刻抓到。
2. **车体航向取了 `front → rear`** —— 车会倒着开；正确定义是"由后转向架指向前转向架"。图形验收时才看出来。
3. **读档后闭环消失** —— 接缝不是父子关系，于是有了 D8 和 `seams[]`。
4. **`Route.radius` 返回带符号的值** —— 右弯轨的"半径"是 −40 m，反直觉；改成恒正，转向由 `dtheta` 的符号表达。
5. **屏幕投影喂错了坐标系** —— `Lens.project` 要的是**镜头节点坐标系**下的点；喂 render 坐标会让"连正对的目标都判为不可见"，表现却只是"端口偶尔选不中"。
6. **`configure_scene` 是从未被调用的死代码** —— 离屏截图脚本自己抄了一份设置，于是 `LColor(*SKY_COLOR)` 少了 alpha 分量这件事一直没暴露，直到第一次真的开窗口才当场 `TypeError`。
7. **20 m 直轨的中间是拾取死区** —— 两个端口在屏幕上相隔两百多像素而拾取半径只有 110 像素，于是"轨道中间指不上去"。修法是把每条 route 的**弧**中点也当抓手。
8. **HUD 的纵向写进了 `z`** —— 全局 `coordinate-system yup` 下 `aspect2d` 的"上"是 `y`、`z` 是进深。写错**不会报错**：四块面板一起塌到屏幕垂直中心，左边一列的文字直接叠在一起，底衬还变成半屏高的黑带。几何断言救不了它（断言自己也用了错的轴），最后是靠**离屏数像素**（"一块面板必须正好一块像素"）才钉住的。
9. **`Scenery.clearance()` 里的"提前跳出"** —— 曾经写成"某个轮廓一旦量到比当前最紧的还紧就跳出"。省下的只是几十个轮廓 × 几百个点，换来的却是：报出来的净距随采样点列的**相位**浮动，而且偏**大**（提前跳出 ⇒ 没量到真正最近的那个点）。表现是"场景自报 18.8 m，独立量出来 19.7 m"—— 一个把"净距"写在 HUD 上给人看的数字，错了却不会有任何报错。这个 bug 是场景测试里那条"自报净距要和独立量测对得上"抓出来的。
10. **`oval()` 的 `side_b` 缺省是"照抄 A"** —— 给 `side_a` 塞了一组道岔（站场那条岔线），对面那条直股就**又长出一个道岔**：环线上凭空多一条岔线，而且它没接尽头线，末端是一段悬空的轨道头。测试只数了"环上有几个道岔"，一下从 1 变成 2。教训是缺省值也要写清"照抄"这件事是有代价的。
11. **视角拖拽方向两个轴都反了** —— 环绕写成了"相机跟着鼠标走"，于是往右拖画面往左跑；用户一眼就看出来。方向在代码里两个正负号都自洽，**只能靠体感发现**，所以修完之后把它变成了断言（§5.10）。同一处还暴露了第二个问题：平移的横向是对的、纵向是反的 —— 两个模式手感不一致比整体反了更难受。
12. **音效改了却"没生效"** —— 合成的 WAV 落在 `%TEMP%` 里按**文件名**幂等复用，于是换了波形之后旧文件被继续用，听起来就是"你改了但我还是听见老声音"，而且看起来完全不像缓存问题。修法是把**修订号写进目录名**（`train3d_sfx_r2`）并在代码里写清"动过波形就 +1"。
13. **`_band_noise` 不能用真随机噪声** —— 第一版宽频轰鸣是"白噪声 + 一阶低通"，听感没问题，但 1 s 循环的接头处必然有个台阶，每圈"咔"一声。测试量的是**接缝台阶 vs 相邻样本步长**，一眼看住（§5.11）。

---

**教训**：第 6 条和第 8 条是同一类 —— **只在真入口才走到的那条路径**（开窗口 / 打开 HUD）没有被任何 headless 测试覆盖。凡是"不报错但画错"的东西，都必须有一条**看图或数像素**的断言兜底。第 11 条是另一类：**不报错、也不算错，只是难用** —— 它没有正确答案可言，只能由人来判，所以判完要立刻固化成断言，否则下次重构又会翻回去。
